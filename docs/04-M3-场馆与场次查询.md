## 4. 设计说明：缓存到底怎么做（本模块核心）

### 4.1 先想清楚：什么该缓存，什么不该缓存

| 数据 | 结论 | 理由 |
|---|---|---|
| 场馆详情 | 缓存，重武器伺候 | 读多写少 + 单 key 热点集中，命中率极高 |
| 场次日历 | 缓存，轻量策略 | 读多但单 key 热度中等，重建成本低（一条索引查询） |
| 搜索列表 | **不缓存** | 城市×类型×关键词×页码 = 笛卡尔积，key 爆炸且绝大多数命中率极低 |

"列表不缓存"是一个容易被忽视的设计点：缓存不是默认开关，**命中率低的缓存只会白吃内存、
还引入一致性负担**。等搜索真成为瓶颈，正确演进是 Elasticsearch，而不是硬塞 Redis。

### 4.2 缓存三件套（`getDetail` 一个方法全讲完）

**① 穿透（查不存在的数据，缓存永远不命中 → 每次都打 DB）**
解法：连"查无此数据"也缓存（空值标记，短 TTL 2 分钟）。恶意脚本循环请求
`id=999999` 时，只有第一次打到 DB，之后 2 分钟内全被 Redis 拦下。
如果考虑布隆过滤器：布隆是前置位图判"一定不存在"，省 Redis 往返、内存极小，
但有误判率和**不能删元素**的短板，适合 id 集合巨大的场景；本项目 id 空间小、
空值缓存已够用 —— 说清取舍比堆技术名词更值钱。

**② 击穿（热点 key 过期瞬间，成千上万请求同时回源 DB）**
解法：`setIfAbsent` 抢互斥锁，只放一个请求去查库重建，其余等待后读缓存；
拿锁后再做一次**双重检查**（排队期间可能已被重建）。
另一条路线是"逻辑过期"（value 里带过期时间，过期后返回旧值+异步重建，
无锁但短暂不一致）。我们选互斥锁：实现直观、数据强一致，等待场景实际很少触发。

**③ 雪崩（一大批 key 同一时刻集体过期 → DB 瞬间被打满）**
解法：TTL = 基础值 + 随机抖动（30~35 分钟），把过期时间打散。
工程上还有第二层：TTL 快到期的热点 key 异步提前续期（逻辑过期思想的组合拳）。

### 4.3 缓存一致性：为什么是"先更新库，再删缓存"

两个常见错误写法先排除：
- **先删缓存再更新库**：删除后、更新前的窗口期，读请求会把**旧值**重新装进缓存，
  脏数据一直活到 TTL 结束；
- **更新库的同时更新缓存**：两个并发写"库顺序"和"缓存顺序"可能相反（A 先写库后写缓存、
  B 后写库先写缓存 → 缓存里是 A 的旧值），且冷数据白白消耗写放大。

标准答案 **Cache Aside：先更新 DB，再删除缓存**。它也有极小概率不一致
（读请求在缓存未命中后查了旧库值，此时写方完成更新+删缓存，读方才把旧值写入），
但发生条件苛刻（读比写慢），概率远低于前两种，**且我们有两道兜底：TTL 到期自愈 +
本模块的删除动作每次写后必执行**。
再往下是"删除失败怎么办"：重试队列 / 订阅 binlog（Canal）异步删 —— 本项目先靠
TTL 兜底，演进路线讲清楚即可。

### 4.4 输入域收敛：缓存系统的隐形防线

`date` 只允许今天起 30 天内、`pageSize` 夹紧到 50 —— 不收敛的话，恶意方可以用
任意日期/页码把缓存 key 打成天文数字（缓存变穿透，Redis 变 DB 放大器）。
**所有进入缓存 key 的用户输入，都必须先收敛到有限集合。**

### 4.5 排期为什么强调幂等

批量排期有两个入口（管理接口 + 每天 00:05 定时任务），重复触发是常态：
失败重跑、人工重跑、未来多实例部署。方案三层：
存在性查询跳过（省 insert）→ `uk_venue_date_time` 唯一索引兜底（并发防重）
→ `DuplicateKeyException` 静默吞掉（少插不重插）。
**凡是"会被重复触发"的写操作，幂等必须做到数据库层。**

### 4.6 双层权限：功能权限 + 数据权限

拦截器的 `@RequireRole(MERCHANT, ADMIN)` 挡住"普通用户进商家接口"（功能权限）；
Service 里再校验 `venue.merchantUserId == 当前用户`（数据权限）——
商家 A 传商家 B 的场馆 id 也进不来。**只做前者是大多数新手项目的通病。**

### 4.7 展示可旧、交易必须准

日历缓存里的 `remainStock` 允许秒级陈旧（用户看到"剩 3 份"下单时其实剩 2 份，
会在下单时被原子校验拦下）——这是"最终一致"在库存场景的正确用法：
**展示层容忍陈旧，交易层严格精确**。反过来把每次浏览都打成强一致读，
DB 会先于业务死掉。

## 5. 踩坑记录

1. **Windows 控制台 GBK**：curl 的 URL/Body 传中文默认 GBK → 服务端解析异常。
   查询参数用 `curl -G --data-urlencode "city=上海"`；请求体用 UTF-8 文件
   `curl -d @file`；日常测试建议直接用 Apifox（恒定 UTF-8）。
2. **memurai-cli 不在 PATH**：装在 `C:\Program Files\Memurai\`，想在命令行查
   Redis 记得补 PATH 或用完整路径；不影响应用本身。
