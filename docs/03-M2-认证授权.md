# M2 · 认证授权（JWT + Redis 双校验 / 注解鉴权）

> 文档版本：v1.0 ｜ 日期：2026-09-15 ｜ 状态：✅ 完成并实测通过（13 个用例）

## 1. 本模块做了什么

| 文件 | 作用 | 关键点 |
|---|---|---|
| module/auth/`JwtUtil` | JWT 签发/解析（jjwt 0.13） | payload 只编码不加密，不能放敏感信息 |
| module/auth/`AuthInterceptor` | 认证+鉴权拦截器 | JWT 本地验签 + Redis 会话校验双保险 |
| module/auth/`RequireRole` | 角色注解 | 方法注解优先于类注解，任一角色放行 |
| module/auth/`CurrentUserContext` | ThreadLocal 上下文 | 用完必须 clear，否则线程复用串号 |
| module/auth/`AuthService` | 注册/登录/登出/me | 先查后插必须配唯一索引兜底 |
| module/auth/`AuthController` | 4 个接口 | /register /login /logout /me |
| module/auth/`AuthProperties` | 类型安全配置 | 密钥 >=32 字节，生产放环境变量 |
| common/constant/`UserRole` | 角色枚举 | 消灭魔法数字 1/2/3/4 |
| common/config/`WebMvcConfig` | 拦截器注册 | 默认拒绝 + 显式白名单 |
| module/system/`AdminController` | 管理员演示接口 | 类级 @RequireRole 验证 403 |
| GlobalExceptionHandler 增强 | 畸形请求体单独处理 | 客户端错误 ≠ 系统事故 |

> 或直接用 Apifox/Postman（它们始终发 UTF-8）。

## 4. 设计说明：为什么这么设计

### 4.1 先分清两个词：认证 vs 授权

- **认证（Authentication）**：你是谁 —— 本模块的登录 + token 校验；
- **授权（Authorization）**：你能干什么 —— `@RequireRole` 角色检查。
对应两个错误码：1010 未登录、1011 无权限，前端据此分别引导"去登录页"和"提示无权限"。

### 4.2 为什么是 JWT + Redis 双层校验

| 方案 | 优点 | 致命短板 |
|---|---|---|
| Session（存服务端） | 可随时注销/踢人 | 分布式要共享存储；水平扩展受约束 |
| 纯 JWT | 无状态、不吃服务端存储 | **签出去就收不回**：改密码/封号/登出，旧 token 在过期前依然有效 |

我们的方案是"JWT 做身份凭证 + Redis 做**会话开关**"：
- JWT 验签/验过期在本地 CPU 完成（第 2 步，零网络开销）；
- Redis 里只存一个短值 `auth:login:{userId} = 当前有效 jti`（第 3 步，一次 O(1) 查询）。

删掉这个 key（登出/封号），所有旧 token 立即失效；换一个新 jti（重新登录），
旧 token 立即互踢。**用一次亚毫秒级的 Redis 查询，换回"可控的会话生命周期"** ——
单机 QPS 几千时这点开销完全可接受，这是典型的工程折中。

### 4.3 单设备登录是怎么顺带实现的

Redis key 按 `userId` 存、值只存"当前那次登录"的 jti。第二次登录覆盖旧值 →
旧 token 校验 jti 不匹配 → 返回"账号已在其他设备登录"。如果产品要多端共存，
把 key 改成 `auth:login:{userId}:{deviceType}` 即可 —— 存储模型决定产品语义。

### 4.4 为什么用拦截器而不是过滤器 / AOP

三者执行时机由外到内：`Filter → Interceptor → AOP`。
- Filter 最靠外，面向 Servlet 容器（编码/跨域/CORS 适合它）；
- **Interceptor 能拿到 HandlerMethod**，也就是"即将执行哪个 Controller 方法"——
  读方法上的 `@RequireRole` 注解只有它方便，所以鉴权选它；
- AOP 面向 Bean 方法内部（业务增强/审计日志/限流，M8 用）。

### 4.5 ThreadLocal 用完必须 clear（真实事故模型）

Tomcat 线程池的线程是**复用**的。请求 A（张三）处理完，ThreadLocal 没清，
线程被复用去处理请求 B —— B 的业务代码 `CurrentUserContext.get()` 拿到的是**张三**，
以张三的身份下单/退款。这是越权 + 内存泄漏的双重事故。
所以 `afterCompletion`（成功/异常都会走）里统一 `clear()`。

### 4.6 登录安全的三个细节

1. **错误提示统一为"用户名或密码错误"**：若区分"用户不存在/密码错误"，攻击者可
   遍历用户名撞库筛选有效账号；
2. **先查后插必须配唯一索引兜底**：并发注册两个同名请求都能通过前置 selectCount，
   最终靠 `uk_username` 的 DuplicateKeyException 兜住（代码里已 catch 转 1021）；
3. **BCrypt 加盐慢哈希**：每次加密盐随机；慢是有意的，抗 GPU 暴力破解。

### 4.7 畸形请求体处理（本次实战新增）

第一轮实测发现：请求体不是合法 UTF-8 JSON 时，异常落到兜底 handler，返回
"系统繁忙"且打了 ERROR 堆栈 —— **客户端错误污染了系统错误告警**，线上会天天误报。
单独增加 `HttpMessageNotReadableException` 处理器返回 1001 并降级为 warn。
原则：**ERROR 日志应该意味着"需要人去看"，分级错了告警就是狼来了。**
