## 4. 设计说明：下单为什么是全项目最难的接口

### 4.1 先看没有防护会发生什么（事故推演）

朴素写法"先查库存再扣减"：
```
线程A: 查库存=1  ──────┐
线程B:   查库存=1  ────┤  两个都看到 1，都认为能订
线程A: 扣减 -> 0      │
线程B: 扣减 -> -1     ┘  超订发生，一份场地卖两个人
```
这是典型的 **check-then-act 竞态**。本方案的六道闸门就是从各个入口堵死它。

### 4.2 六道闸门逐个拆解

**① 幂等凭证**：前端先领一次性 token（绑定 userId，5 分钟有效），下单时用 Lua
"值匹配才删除"原子消费。为什么必须 Lua：GET 和 DEL 分两步的话，两个并发重放请求
都 GET 到了值 → 都通过 → 幂等失效。**任何"检查+行动"两步操作在并发下都必须原子化。**

**② 用户级分布式锁（锁粒度设计）**：
- 锁"整个下单流程"（全局锁）→ 所有用户串行，吞吐归 1，不可接受；
- 锁"场次"→ 只有抢同一场次的人串行，看似合理，但限订校验等读操作也被串行化，
  且不同用户之间本来就不需要互斥；
- **锁"用户"**：只串行化同一用户的并发请求（防双击），不同用户完全并行，
  冲突交给后面的 Lua + 条件更新。**锁应该只锁真正有竞争的最小资源。**

**③ 限订校验**：同用户同场次只允许一笔 0/1 状态订单——因为锁在外层，
这个"查+插"是串行的，不会被并发击穿（多实例下靠的正是 Redisson 锁的分布式语义）。

**④ 快照**：价格/场馆名/时间从场次行读出后**复制进订单**——之后商家改价不影响
已建订单，详情展示也不需要联表。

**⑤ Redis Lua 原子预扣**：`GET→判断→DECR` 在 Redis 单线程里整体执行
（Redis 执行 Lua 期间不插入其他命令），把 50 个并发里的 38 个在 Redis 层就挡掉，
DB 只见 12 个"真有戏"的请求。这就是**流量漏斗**：Redis 扛量，MySQL 扛正确性。

**⑥ MySQL 条件更新兜底**：`UPDATE ... SET remain=remain-1 WHERE id=? AND remain>0`，
InnoDB 行锁天然串行化对同一行的修改，**影响行数=0 即没抢到**——这是乐观锁的
"条件更新"形态（另一种是 version CAS，适合普通并发编辑；库存场景条件更新更直接）。
它是最终防线：即使 Redis 数据漂移，DB 也不会卖出第 13 份。

### 4.3 两级库存的一致性三条规则

Redis 是"预扣计数器"，MySQL 是"最终事实"。本项目守住一致性的三条规则：
1. **DB 失败必回补**：条件更新 0 行或插入订单异常 → `INCR` 把 Redis 预扣还回去
   （事务回滚后 Redis 若不还，库存凭空蒸发）；
2. **初始化用 SETNX**：stock key 首次不存在时从 DB 读值 `setIfAbsent`——
   如果用普通 SET，"别人已扣减后又被旧值覆盖"的竞态会造成永久漂移；
3. **以 DB 为准**：Redis 有余量但 DB 扣减 0 行 → 按"没库存"处理并回补 Redis。
终极兜底是 M8 的对账任务（定时比对两级库存）。

### 4.4 为什么用编程式事务（本次的真实设计决策）

分布式锁必须在**事务提交之后**才能释放。`@Transactional` 的提交发生在代理层
（方法返回之后），如果在同一个方法里 finally 解锁，顺序变成"解锁 → 提交"，
下一个拿到锁的请求读不到上一笔未提交的订单，限订校验被击穿。
解法：`TransactionTemplate` 把事务边界显式化——锁在外、事务在内、提交完成才放锁。
（另一解法是拆两个 Bean 让代理生效，但显式事务更能表达这个顺序约束。）

### 4.5 Redisson 的三个细节

1. `tryLock(3, 10, SECONDS)`：最多等 3 秒，锁 10 秒自动过期——持有者崩溃也不会死锁；
2. 显式 leaseTime 下看门狗不生效；若业务时长不可预估，用 `tryLock(wait)` 让看门狗
   自动续期（看门狗：Redisson 后台线程定期把锁 TTL 续回 30s）;
3. 解锁前 `isHeldByCurrentThread()`：锁过期易主后不误删别人的锁
   （M3 详情缓存里的简化锁就有这个缺陷，M4 升级为正确示范）。

### 4.6 雪花算法订单号

64 位 = 1 符号 + 41 时间戳（毫秒，69 年）+ 5 机器号 + 12 序列（单机每毫秒 4096 个）。
不用自增的理由：可遍历（泄露单量）、分库分表冲突、无时间信息。
实测 12 个并发单号单调递增且唯一。时钟回拨直接拒绝发号——宁可失败不产重复 ID。

### 4.7 压测数字的解读

"50 并发抢 12 份库存：12 成功 / 38 拒绝 / DB 与 Redis 库存双双归零 / 零超订 / 零异常。
如果没有闸门 5，50 个请求全部打到 DB 行锁上排队；如果没有闸门 6，Redis 一旦漂移
就会超订；如果没有闸门 1，一次网络重试会生成两笔订单。"
——把每个数字对应到一道闸门，比堆数字有说服力。

## 5. 踩坑记录

**bash 裸 `wait` 挂起测试脚本**：压测脚本里 `wait` 不带参数会等待本 shell 的
**所有**后台任务——包括一直运行的应用 java 进程，脚本永远停在"压测中"。
修复：收集每个 curl 的 PID，`wait "${PIDS[@]}"` 只等并发请求。
教训：并发脚本里 `wait` 必须指明等待对象，自动化测试卡住先查"在等谁"。
