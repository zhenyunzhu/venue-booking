## 2. 实测记录

### 2.1 限流（每用户 3 次/10 秒，抢券接口）

```
第1~3次 → 业务响应（1062 限领）          ← 限流放行
第4~5次 → {"code":1401,"message":"请求过于频繁（3次/10秒）..."}  ← 拦截
等 11 秒窗口滑过 → 恢复业务响应            ← 滑动窗口语义正确
```

**真实踩坑**：初版 Lua 把清理上界写成"当前时间"，
`ZREMRANGEBYSCORE key 0 now` 把刚计入的请求一起清掉 → ZCARD 恒为 0 → 永远放行。
正确语义是清理"窗口起点之前"的成员（now - windowMs）。**测试发现 → SQL/脚本日志
定位 → 边界条件修复**——完整排查链见 docs/08 同款方法论。

### 2.2 两级库存对账

```
人为污染 Redis stock:slot:23 = 999（DB=10）
POST /api/admin/reconcile → {"data":["slot 23: redis 999 -> db 10"]}
修复后 Redis = 10 ✓
```

### 2.3 慢 SQL 调优（真实 EXPLAIN 输出）

| 查询 | type | key | 结论 |
|---|---|---|---|
| 场馆搜索 (city+type+status) | ref | idx_city_type_status | 联合索引命中，最左前缀 |
| 我的订单 (user_id+status) | range | idx_user_status | 联合索引 range |
| 关单扫描 (status+expire_time) | range | idx_expire | 为定时任务专建的索引 |
| 反面：remark LIKE '%x%' | **ALL** | NULL | 前导通配全表扫，量大会拖垮库 |
| 覆盖索引 (id,order_no,user_id) | ref | idx_user_status | Extra 无 Using index condition，免回表 |

调优方法论：**explain 观察 type/key/rows/Extra → 定位全表扫与回表 → 建联合索引
（区分度高的列在前）→ 业务上消除前导通配**。模糊搜索的真实解法是 ES（M3 已埋伏笔）。
