# 工程化与发布准备（从"能跑"到"能发布"）

> 本文档记录把项目从"教学实现"推进到"可发布 GitHub 状态"的全部工程化改造，
> 以及发布步骤。

## 1. 四个差距的落实清单

### 差距① 单元测试（最关键）→ ✅ 16 个用例

| 测试类 | 类型 | 覆盖 |
|---|---|---|
| SnowflakeIdGeneratorTest | 纯单元 | 严格递增、**8 线程并发唯一性**、非法机器号拒绝 |
| RefundRuleCalculatorTest | 纯单元 | 2 小时整/差 1 分钟/已开场三边界、金额舍入 |
| CouponDiscountCalculatorTest | 纯单元 | 满减/折扣/零优惠/**优惠封顶防倒贴** |
| BookingFlowIntegrationTest | @SpringBootTest 集成 | 正常下单、凭证重放、重复下单、零库存拒绝、单号唯一 |

工程手法：把退款规则、优惠计算从 Service 私有逻辑**抽成纯函数类**
（RefundRuleCalculator / CouponDiscountCalculator）——规则是资金敏感、边界密集的
逻辑，抽成无依赖的纯函数后可以穷举测试，不需要启动整个应用。
集成测试用 @SpringBootTest 起完整上下文打真实 MySQL/Redis，
测试数据自治理（唯一键冲突规避 + AfterAll 物理清理）。

### 差距② 配置脱敏 → ✅ 环境变量占位

```yaml
password: ${MYSQL_PASSWORD:123456}        # 冒号后为本地开发默认值
jwt-secret: ${JWT_SECRET:venue-booking-demo-...}
notify-secret: ${PAY_NOTIFY_SECRET:demo-pay-...}
```
公共仓库中不再出现"看似真实"的密码；生产用环境变量/配置中心注入。
docker-compose 演示了这套机制的实际用法（MYSQL_URL / REDIS_HOST）。

### 差距③ API 文档 / CI / 容器化 → ✅ 三件齐备

- **SpringDoc 2.9.1**（Boot 3.x 对应版本线，注意 3.x 是给 Boot 4 的）：
  `/swagger-ui.html` 可视化调试，Authorize 支持 Bearer token；
- **GitHub Actions**（.github/workflows/ci.yml）：push/PR 自动以 services 容器拉起
  MySQL+Redis → 初始化库表 → `mvn package` 跑全量测试——CI 红灯挡住坏提交；
- **Dockerfile 多阶段构建**（Maven 编译层 + JRE 运行层，依赖层缓存）+
  **docker-compose**（MySQL 自动执行建表脚本 + Redis + 应用互访），
  新人克隆后 `docker compose up -d` 一条命令起全环境。

### 差距④ 模拟实现标注 → ✅ README 专节 + 代码注释

诚实列出：模拟支付、MD5 验签、即时退款、日志模拟短信、per_limit>1 无强校验、
单实例定时任务——每项都给了生产扩展路径。**主动暴露边界是工程可信度的来源**。

## 2. 发布到 GitHub 的步骤

```bash
cd venue-booking
git init
git add -A
git commit -m "feat: 趣订场-场馆预订与核销平台（含压测验收/测试/CI/文档）"
git branch -M main
git remote add origin https://github.com/<你的用户名>/venue-booking.git
git push -u origin main
```

发布前自查三件事：
1. `git status` 确认没有 target/、日志等构建产物（.gitignore 已覆盖）；
2. README 里的 CI 徽章地址换成你的仓库路径（或删除）；
3. 推送后到 Actions 页确认第一次 CI 全绿。
