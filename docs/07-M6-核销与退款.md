## 3. 设计说明

### 3.1 核销为什么不需要分布式锁

两个核销员同时扫同一码：`UPDATE ... SET status=2 WHERE checkin_code=? AND status=1`
——InnoDB 行锁自动串行化，先到者影响行数=1，后到者=0 走幂等分支。
**单行条件更新本身就是原子的，锁是多余的**；分布式锁只用于"多条语句组成的
临界区"（如下单的查+扣+插）。

### 3.2 退款防重的双保险

重复退款是资金级事故。两道防线：
1. **Redisson 锁 orderNo**：把"查状态→算金额→改状态→立退款单"整段串行化，
   防止两个请求同时读到 status=1；
2. **状态机条件更新 1→6**：即使锁因异常失效，第二个请求影响行数=0 也会被拒。
   防线设计原则：**任何单点防护都要假设它会失效**。

### 3.3 退款规则引擎的演进路径

当前是 if-else 规则（>=2h 全额 / <2h 扣 30% / 已开场不可退）。
规则多了之后的演进：规则表（DB 配置化）→ 策略模式 + 规则链 → Drools 类规则引擎。
关键在于知道什么时候不该上规则引擎，而不是堆框架。

### 3.4 退款单为什么独立于订单

订单表记"结果"（status=6），退款单记"过程"（退了多少、退款单号、谁审的、
何时到账）。资金链路三要素：**可追溯（单号链）、可对账（金额勾稽）、可审计（留痕）**。
生产中退款是 1→5(退款中)→6，等待第三方退款回调确认。

### 3.5 真实踩坑：select 部分列的静默陷阱（两连坑）

第一坑：select 漏查 userId → `order.getUserId()` 自动拆箱 NPE（幸好异常可见）；
第二坑：select 漏查 orderNo → `WHERE order_no = null` 永远匹配不到行 →
**不报错、只返回"状态不对"**，比 NPE 更难查。最后靠 MP 的 SQL 日志
（`Parameters: null, 4`）一眼定位。
教训：**用 `.select()` 只查部分列时，实体里其他字段全是 null；要么查全列，
要么把需要的值作为方法参数显式传递**。排查依赖：开发期开 SQL 日志。
