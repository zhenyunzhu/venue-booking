## 3. 设计说明

### 3.1 抢券与抢场次：同构但不同配置

两个秒杀场景共用同一套骨架（Lua 预扣 → 条件更新兜底 → 失败回补），差异在业务约束：

| 维度 | 场次抢订 | 抢券 |
|---|---|---|
| 强一致诉求 | 高（同用户同场次限一单） | 低（多领一张券损失可控） |
| 并发锁 | Redisson 用户锁 | **不加锁**，SETNX 限领标记替代 |
| 流量特征 | 日常+放票峰值 | 活动瞬时洪峰（更陡） |

**没有一种秒杀方案包打天下——按业务容忍度配置一致性强度**，这是 M7 的核心结论。

### 3.2 SETNX 限领标记的取舍

`SET coupon:got:{cid}:{uid} 1 NX EX {活动结束}`：原子防重领，还天然带过期。
代价：per_limit>1 时标记模型不适用（当前代码对 per_limit=1 才启用），
且"抢券成功但落库失败"的回补路径要**连标记一起删**，否则用户被永久误伤。
如果 Redis 标记和 DB 不一致：标记只做前置过滤，
真正的限额兜底是持券记录 + 对账（M8），允许极小概率多发的业务损失。

### 3.3 用券为什么不做"券秒杀"

用券（核销持券）是低频写，走**纯事务**：校验（读）在前，占用（条件更新 0→1）
与订单插入同事务——并发重复用券只有一个 rows=1，失败整体回滚（含已扣的场次库存，
Redis 回补逻辑自动覆盖）。读校验+写占用的分离是标准做法：**读可以宽松，写必须原子**。

### 3.4 踩坑记录

测试脚本用响应里不存在的 `couponId` 字段解析持券 ID → 解析为空 → 请求体非法。
定位后确认业务代码无缺陷。教训：**测试断言要先对齐接口契约（VO 字段）**；
另外 1053 拦截了"遗留待支付订单未取消就再下单"——防重逻辑在真实数据上正确工作。
