## 3. 设计说明

### 3.1 多级缓存：为什么 L1 快，为什么会脏，怎么治

- **L1（Caffeine，进程内）**：读内存无网络往返，纳秒级；Redis 再快也有 ~1ms 网络往返
  和序列化开销。热点场馆 QPS 上万时 L1 顺带保护 Redis。
- **为什么会脏**：L1 在各实例自己的内存里，实例 A 更新了场馆，实例 B 的 L1 还留着
  旧值——Redis 那套"删缓存"够不着别人的内存。
- **怎么治**：更新时删 L2 + **Pub/Sub 广播失效**，所有实例订阅频道各自驱逐 L1。
  但广播 fire-and-forget、实例宕机会漏收——所以 L1 只给 60 秒短 TTL 作为
  **最大不一致窗口兜底**。可靠性靠 TTL、及时性靠广播，两层配合。
- 延伸：这个广播机制就是"简易版 Redisson RLocalCachedMap"；
  更大规模用 MQ 广播或版本号协商。

### 3.2 布隆过滤器：把穿透挡在最前面

位数组 + 多哈希：**说不存在就一定不存在（零漏判），说存在可能误判（配置 1%）**。
所以它只做"快速否定"，命中后照常走缓存链。与 M3 空值缓存的分工：
布隆挡"从未存在的恶意 id"（内存恒定，不随攻击增长）；空值缓存兜"下架/误判漏网"。
**不能删除元素**是它的招牌短板——本系统逻辑删除使 id 永远有效，正好规避；
真实删除场景要用计数布隆或定期重建。

### 3.3 Outbox 本地消息表：没有 MQ 的"事务消息"（本里程碑含金量最高）

**问题**：支付成功后要发核销通知。直接调用的话，进程在"事务提交后、调用完成前"
崩溃，这个事件就永久丢了——用户付了钱，永远等不到核销码。

**方案**：把"发消息"变成"写本地表"，与支付**同一事务**：
```
事务 { UPDATE 订单已支付; INSERT t_outbox_message(PAY_SUCCESS); }  —— 同生共死
中继任务(每10s) { 扫描到期消息 → handler 执行下游 → 标记完成 }
失败 → 指数退避重试(2^n 分钟) → 超过 5 次进死信表状态，人工介入
```
- **发布幂等**：唯一索引 (biz_type, biz_key)，重复回调重复 publish 被静默忽略；
- **投递语义 at-least-once**：可能重复投递（处理成功但标记完成前崩溃），所以
  消费端 handle 必须幂等——这是 Outbox 的铁律；
- **消费抢占**：每条消息 Redisson 非阻塞锁，多实例不重复消费；
- **与 MQ 事务消息对比**：RocketMQ 半消息是中间件代做 Outbox；本地消息表
  零依赖、消息可靠性与业务数据同库同备份，代价是消费方要自己实现（本项目
  30 行中继任务）。演进：消息量大或需要广播/重试策略托管时换 RocketMQ，
  业务代码只需把 publish 的实现类换掉。

### 3.4 可观测性：先能"串"，再能"量"

- **traceId**：Filter 每请求生成（或透传上游 X-Trace-Id）→ MDC → 日志行 → 响应头。
  排查动作从"翻半小时日志碰运气"变成"拿 traceId 一屏看完"。
- **业务指标**：下单成功数、库存拒绝数、限流拦截数、缓存 L1/L2 命中、布隆拦截——
  技术指标告诉你"不舒服"，业务指标告诉你"哪里不舒服"。
  实测的指标读数与测试动作一一对应，这就是可解释性。

### 3.5 游标分页：页码分页的性能悬崖

`LIMIT 100000, 20` 要扫过并丢弃 100020 行，越翻越慢，且新数据插入导致页码漂移
（重复/漏读）。游标分页 `WHERE id < lastId ORDER BY id DESC LIMIT n`：
B+ 树直接定位，性能恒定、不漂移；代价是没有跳页。**订单流/信息流这类"连续刷"
场景一律游标**，管理后台跳页场景才用页码。
