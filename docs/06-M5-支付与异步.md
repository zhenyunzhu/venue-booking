## 4. 设计说明

### 4.1 回调幂等为什么要三保险

第三方回调的真实可靠性模型是"**至少一次投递**"——网络抖动时同一笔回调会来 2、3 次。
- **第一层 trade_no 唯一索引**：最常见的重复（同一笔交易重放）在 DB 层直接拦截，不依赖代码写对；
- **第二层状态机条件更新**（0→1，影响行数判断）：不同交易号但订单已支付的并发回调，走到这里被分支为"幂等成功返回"；
- **第三层同一事务**：流水与订单状态同生共死，杜绝"用户扣了款、系统没出票"的资金事故。

### 4.2 两个鉴权模型（一个常被忽视的点）

用户接口走 JWT；**支付回调是服务端对服务端，走验签不走 JWT**——如果回调接口落在
JWT 拦截器保护内，第三方根本调不进来；如果不加验签裸奔，任何人 POST 一下就能把
订单改成已支付。我们用 `md5(orderNo|secret)` 模拟，生产是平台签名+证书验签+IP 白名单。

### 4.3 延迟队列 vs 定时轮询（双保险哲学）

- 轮询：实现简单，但有扫描间隔误差、大表条件扫描慢查询、大量空转；
- Redisson DelayedQueue：到点精准投递、零空转，`take` 阻塞消费；
- **两者都要**：队列保证时效性，扫描保证最终一致性（消息可能因重启丢失）。
多实例部署时 `take` 语义天然保证一条消息只被一个实例消费。

### 4.4 关单的幂等性

关单动作 = `UPDATE status 0→4 WHERE order_no=? AND status=0`。重复执行影响行数=0
直接跳过——**用数据库行锁+条件更新实现幂等，不需要额外的锁**。回补库存只发生在
影响行数=1 的分支里，绝不重复回补。

### 4.5 真实踩坑：@Transactional 自调用失效

初版 `mockPay()` 内部 `this.handleNotify()`——**同类自调用绕过 AOP 代理**，
事务注解静默失效，`registerSynchronization` 抛异常返回 2000，而流水/订单已各自
自动提交，状态割裂。修复：改用 `TransactionTemplate` 显式控制事务边界，
通知/取消关单消息等副作用放在事务返回（=提交）之后执行。
这个坑的通用启示：**Spring 的事务/异步/缓存注解都基于代理，自调用、final 方法、
非 public 方法都会静默失效——失效比报错更危险。**

### 4.6 Redisson 4.x 的弃用提示

日志里有一条 `RDelayedQueue object is deprecated... Use RReliableQueue`（Redisson
以 ERROR 级别打弃用告警）。功能完全可用，本项目保留 RDelayedQueue 便于理解原理；
生产升级路径是 RReliableQueue（带确认重投）。
