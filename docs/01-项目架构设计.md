## 1. 项目定位（一句话）

**趣订场**是一个面向线下运动场馆（羽毛球/篮球/游泳等）的**在线预订与到店核销平台**：
用户按"场次"抢订场地 → 在线支付获取核销码 → 到店扫码核销；商家管理场馆排期与分时段定价；
平台支持取消退款、限时抢券、候补排队。

## 2. 选题背景与价值

1. **场景真实、一听就懂**：预约制是线下业态的普遍形态（场馆/自习室/诊所/充电桩），
   但候选人里做"订场核销"的极少，避开了"第 N 个商城/外卖/点评"的同质化红海。
2. **并发模型 = 秒杀同款，但换了皮**：黄金场次（周五晚 8 点放票）就是抢票/秒杀，
   "防超订"与电商"防超卖"完全同构——你练的是最值钱的高并发交易能力，却没有撞题。
3. **亮点密度高**：一个项目天然覆盖三大核心能力——缓存体系（穿透/击穿/雪崩 + 一致性）、
   分布式锁与库存扣减、接口幂等与限流，外加延迟队列、状态机、线程池异步化。
4. **"抢券"是第二个秒杀场景**：营销模块的限时抢券体现了"两种秒杀对象
   （时段库存 / 券库存）的不同处理"，体现方案沉淀能力。
5. **可演进性好**：模块化单体边界清晰，可按业务域拆分微服务（用户/场馆/交易/营销）。

## 3. 角色与核心用例

```
普通用户：注册登录 / 搜索场馆 / 查看场次日历 / 抢订下单 / 模拟支付 / 查看核销码
          / 取消退款 / 领券用券 / 排候补 / 评价
场馆商家：场馆上下架 / 场次模板与定价 / 批量生成场次 / 核销（输码） / 经营数据
平台管理员：用户管理 / 场馆审核 / 全局数据看板
```

## 4. 总体架构（模块化单体）

```
                    ┌────────────────────────────────────────────┐
  Apifox/Postman →  │              Spring Boot 3.5 单体           │
                    │                                            │
                    │  接入层：Controller（按业务域分包）           │
                    │  横切：  AuthFilter(JWT) │ 全局异常 │ 统一响应 │
                    │         @RateLimit 限流AOP │ 操作日志AOP      │
                    │  业务层：venue / slot / booking / payment /  │
                    │         refund / checkin / coupon / ...     │
                    │  数据层：MyBatis-Plus Mapper                │
                    └───────────────┬───────────────┬────────────┘
                                    │               │
                              MySQL 8.0         Redis 7
                             （业务数据）    （缓存│锁│延迟队列│限流计数）
```

**Redis 在本项目承担 4 个角色，每个角色对应一个核心设计点：**

| 角色 | 用途 | 对应亮点 |
|---|---|---|
| 缓存 | 场馆详情/场次日历高频读 | 穿透/击穿/雪崩治理 + 缓存一致性方案 |
| 分布式锁 | 防重复下单、防重复退款、防重复核销 | Redisson + 看门狗，锁粒度设计 |
| 延迟队列 | 订单 15 分钟未支付自动关单、候补通知 | Redisson DelayedQueue，为什么不用轮询 |
| 限流计数器 | 放票洪峰/抢券洪峰的接口限流 | 自定义注解 + AOP + Lua 滑动窗口 |

**为什么引入 MQ？——本项目刻意不引入**：本地环境只需 MySQL + Redis，调试成本最低；
所有异步/延迟用 Redis 方案实现（规模评估 → Redis 方案的可靠性边界 → 如果上 RocketMQ 如何平替）。

## 5. 包结构（package-by-feature，按业务域分包）

```
com.venuebooking
├── VenueBookingApplication.java
├── common/                     # 与业务无关的通用组件
│   ├── result/                 #   Result<T> 统一响应、错误码枚举
│   ├── exception/              #   BizException、全局异常处理器
│   ├── mybatis/                #   MP 分页/乐观锁插件、字段自动填充
│   ├── redis/                  #   Redis 配置、工具类、Lua 脚本加载
│   └── util/                   #   ID 生成、JSON、断言工具
└── module/                     # 业务模块
    ├── auth/                   # 注册登录、JWT、鉴权拦截器、@RequireRole
    ├── user/                   # 用户资料
    ├── venue/                  # 场馆管理（商家侧）
    ├── slot/                   # 场次模板、批量生成、场次日历查询
    ├── booking/                # ★预订订单（核心链路）
    ├── payment/                # ★模拟支付、回调幂等
    ├── refund/                 # 取消退款、库存回补
    ├── checkin/                # 核销
    ├── coupon/                 # ★限时抢券、下单抵扣
    ├── review/                 # 评价
    ├── waitlist/               # 候补
    └── notify/                 # 站内信、异步通知
```

每个 module 内部再按 `controller / service / mapper / entity / dto` 分层。
**为什么按业务分包而不是按技术分包**：模块内高内聚、模块间只经 service 互调，
将来拆微服务时按 module 直接搬走（这是"如何演进到微服务"的标准答案素材）。

## 8. 数据库设计

### 8.1 表清单（12 张，全部含注释，可直接 DataGrip 执行）

| 表 | 用途 | 关键设计点 |
|---|---|---|
| t_user | 用户 | BCrypt 密码；phone 可空 + 唯一索引（NULL 不冲突） |
| t_venue | 场馆 | court_count=场地数=库存总数；(city,type,status) 联合索引支撑首页筛选 |
| t_slot_template | 场次模板 | 商家定价配置，批量生成场次的来源 |
| t_venue_slot | **场次=时段库存** | 唯一键(venue,date,start)防重复生成；remain_stock 扣减防超订；version 乐观锁 |
| t_booking_order | **预订订单** | 状态机 0~6；冗余场次快照免联表；(status,expire_time) 索引支撑关单扫描 |
| t_payment_record | 支付流水 | trade_no 唯一索引=回调幂等的 DB 兜底 |
| t_refund_record | 退款单 | 退款与订单分离，资金操作留痕 |
| t_coupon / t_user_coupon | 券模板/持券 | remain_count 抢券扣减；持券表冗余快照防模板改价影响历史订单 |
| t_review | 评价 | 一单一评（唯一索引兜底），评分冗余回写场馆 |
| t_waitlist | 候补 | 唯一键(slot,user)防重复排队 |
| t_notify_message | 站内信 | 异步通知的落库凭证 |

### 8.2 核心关系

```
t_user 1──n t_booking_order n──1 t_venue_slot n──1 t_venue 1──n t_slot_template
   │1              │1                    │1
   │               ├──── 1:1 ──── t_review
   │               ├──── 1:n ──── t_payment_record / t_refund_record
   │               └──── 0:1 ──── t_user_coupon（用券）
   ├──── 1:n ──── t_user_coupon / t_notify_message
   └──── 1:n ──── t_waitlist ── n:1 ── t_venue_slot
```

### 8.3 设计原则（逐条理解理由）

1. **不建物理外键**：外键约束带来锁竞争与级联风险，且不利于分库分表与数据订正；
   一致性由应用层（事务+状态校验）保证。
2. **金额一律 DECIMAL**：float/double 二进制浮点存不了精确的 0.1 元，对账必出事。
3. **乐观锁 version + 影响行数判断**：并发扣库存 `UPDATE ... SET remain=remain-1
   WHERE id=? AND remain>0`，靠 MySQL 行锁串行化，影响行数=0 即抢失败。
4. **快照冗余**（订单里的场馆名/单价/场次时间）：历史订单不能随场馆改名/调价漂移，
   同时详情页免联表。
5. **唯一索引兜底幂等**：order_no/checkin_code/trade_no/uk(venue,date,start)——
   并发重试的最后一道闸门是数据库，不是代码。
6. **逻辑删除 + 状态字段用 TINYINT + 注释枚举**：可读性与运维友好。

## 9. 核心链路设计（M4/M5 按此实现）

### 9.1 抢订下单（防超订三道闸）

```
用户点击"立即预订"
 │ ① 幂等闸门：Redis 下单 token / 请求指纹 —— 同一请求重复提交直接拦截
 ▼
② Redis 闸门：Lua 脚本原子"查库存+扣减" —— 单线程执行，挡掉 99% 无效流量
 ▼
③ MySQL 闸门：事务内 UPDATE t_venue_slot SET remain_stock=remain_stock-1
   WHERE id=? AND remain_stock>0 → 影响行数=0 则整体回滚（Redis 回补）
   + INSERT 订单（待支付，15 分钟过期）
 ▼
④ 引导支付 → 支付回调（幂等：trade_no 唯一索引 + 订单状态机校验）
 ▼
⑤ 支付成功：生成核销码 + 异步发站内信（线程池，不让通知拖慢主链路）
```

不这么写会怎样：①没有 → 用户狂点生成 N 笔订单；②没有 → 所有请求直接打到 MySQL，
行锁排队拖垮库；③没有 → Redis 与 MySQL 网络抖动/宕机时超订（钱和场地都要出问题）。

### 9.2 超时关单（延迟队列）

下单时投递 15 分钟延迟消息（Redisson DelayedQueue）→ 到期消费：
查订单状态仍为"待支付"→ 关单 + MySQL 回补库存 + Redis 回补 + 通知候补队列。
对比定时轮询扫描：扫描有延迟、空轮询浪费、量大时慢查询；延迟队列精准且无空转。

### 9.3 取消退款

规则引擎（开场前 2h 免费退，之后扣 30%）→ 生成退款单 → 原路退回（模拟）→
订单转已退款 → 库存回补 → 触发候补通知。全程分布式锁锁订单号，防并发重复退款。

## 10. 接口与工程规范

- **统一响应**：`Result<T> { code, message, data }`；业务错误码分段：
  A-用户侧(1xxx) / B-系统侧(2xxx) / C-第三方(3xxx)。
- **参数校验**：`spring-boot-starter-validation` + `@Validated`，非法入参 400 统一格式。
- **RESTful 约定**：资源名词复数、动作靠 HTTP 方法；非 CRUD 动作用动词子路径
  （如 `POST /api/bookings/{orderNo}/cancel`）。
- **分页**：MyBatis-Plus `Page<T>`，响应里带 total/pages。
- **Git**：main 保持可运行，每个里程碑一个 feature 分支合并，保证可追溯的迭代过程。
